# BDD `.feature` vs 手写 JSON workflow — 量化对比测试报告

> **日期**: 2026-10-12（§6 于 2026-10-14 复核到 14 个 authoring 任务的当前数字）
> **环境**: laya-workflow release binary（构建于 2026-10-11，HEAD `71fb20e`），本地离线执行，无网络依赖
> **语料**: `bdd/workflows/browser/*.feature` — 29 个真实网站 workflow（每个 >20 步，覆盖 Wikipedia/GitHub/PyPI/arXiv 等 29 个外部站点；另有 `_probe.feature` 探针不计入语料；2026-10-13 起语料源从 `bench/bdd/live/` 移至此处，`bdd compare` 结果数字不变）
> **对照定义**: 「BDD」= `.feature` 源文件（作者手写）；「JSON」= 同一 workflow 经 `bdd transpile` 编译出的 spec（即手写 JSON DSL 需要表达的等价内容）
> **原始数据**: `bench/bdd/metrics_raw_20261012.json`（所有数字可复现；`metrics2`/`extra` 中含 `_probe` 探针共 30 行，报告均值已剔除该探针按 29 case 计算）
> **复现**: `laya-workflow bdd compare` / `bdd score` + `bench/bdd/metrics_raw_20261012.json` 内记录的各子脚本

---

## 0. 结论速览（12 类指标）

| # | 指标 | BDD `.feature` | 手写 JSON DSL | 比值 | 判定 |
|---|------|---------------:|--------------:|-----:|------|
| 1 | 体积：字节（29 case 总计） | 51,958 B | 832,004 B | **16.0×** | BDD 省 93.8% |
| 2 | 体积：行数（29 case 总计） | 958 行 | 36,266 行 | **37.9×** | BDD 省 97.4% |
| 3 | 单 workflow 平均行数 | 33.0 行 | 1,250.6 行 | 37.9× | — |
| 4 | 单 workflow 平均词数/JSON token | 230.0 词 | 3,448 JSON token | 15.0× | — |
| 5 | 编译/校验时延（中位数，5 次重复） | 5.4 ms（transpile） | 4.5 ms（validate） | ≈1× | **两者都免费** |
| 6 | 编译/校验时延（P95） | 6.6 ms | 5.7 ms | ≈1× | — |
| 7 | 改一个 URL 需触碰的行数 | **1.3 行** | 3.6 行 | 2.8× | BDD 改动面小 |
| 8 | JSON 产物重复行占比 | — | **86.9%** | — | 样板噪音极高 |
| 9 | JSON 嵌套深度 | — | 恒为 6 层 | — | 人读负担重 |
| 10 | 语义故障检出率（BDD 3 类×20 / JSON 5 类×20） | **60/60 = 100%** | 20/100 = 20% | **5×** | BDD 胜 |
| 11 | 语法/截断故障检出率 | 40/40 = 100% | 40/40 = 100% | 1× | 平手 |
| 12 | 诊断带行号率 | 66.7%（语义）/ 85%（截断） | 0%（语义）/ 100%（截断） | — | BDD 语义诊断强 |

**一句话**：同一批 29 个真实 workflow，BDD 源文件比它编译出的 JSON **小 16 倍（字节）/38 倍（行）**，改同一处 URL 少碰 2.8 倍的行，注入 60 个语义故障 BDD 编译期全抓（100%）、JSON `validate` 只抓结构性的 20%；而两者的机器处理时延都是个位数毫秒，**没有任何速度代价**。

## 1. 指标 1–4：表达体积（作者要写多少）

来源：`laya-workflow bdd compare`（离线，29 case）。

| 量 | BDD | JSON | 比值 |
|---|----:|-----:|-----:|
| 总字节 | 51,958 | 832,004 | 16.0× |
| 总行数 | 958 | 36,266 | 37.9× |
| 平均每 workflow 行数 | 33.0 | 1,250.6 | 37.9× |
| 平均每 workflow 词/token | 230.0 词 | 3,448 JSON token | 15.0× |
| 编译产物平均字段数 | — | 762 | — |
| 平均步骤数 | 29.0 | （编译出 28.0 op/node） | ≈1:1 |

**关键观察**：比值不是恒定的——行数比（37.9×）远大于字节比（16.0×），因为 JSON 每个字段单独占行、且含大量重复样板（见指标 8）。**按行读/写，差距比按字节看更大。**

## 2. 指标 5–6：机器处理时延（免费吗？）

方法：每个 case 重复 5 次，取中位数（含进程启动）。

| 操作 | 中位数 | 均值 | P95 | 范围（29 case） |
|---|---:|---:|---:|---|
| BDD `transpile`（.feature → spec） | **5.4 ms** | 5.6 ms | 6.6 ms | 4.7–8.3 ms |
| JSON `validate`（spec → 校验） | **4.5 ms** | 4.7 ms | 5.7 ms | 4.1–6.0 ms |

**两者差异 <1 ms，对任何 CI / 编辑器 loop 都不可感知。** BDD 的编译不是性能税。

## 3. 指标 7：修改摩擦（改一处要动多少行）

方法：取每个 workflow 编译产物中的目标 URL/selector，在源文件与产物中数「含该值的行数」，10 case 采样。

| case（示例 3） | 需改行（BDD） | 需改行（JSON） |
|---|---:|---:|
| `02_wikipedia_rust`（改 URL） | 1 | 3 |
| `06_hackernews`（改 URL） | 2 | 5 |
| `10_docsrs_serde`（改 URL） | 1 | 3 |
| **均值（10 case）** | **1.3** | **3.6** |

**JSON 是 2.8× 的改动面**，且 1 个语义值在 JSON 中平均重复出现 3–5 次（source url + 各处引用），漏改一处即不一致；BDD 中 URL 通常只出现 1–2 次。

## 4. 指标 8–9：结构噪音

| 量 | 值 |
|---|---:|
| JSON 产物重复行占比（29 case 均值） | **86.9%**（范围 86.8–87.9%） |
| JSON 最大嵌套深度 | 恒为 **6 层** |
| BDD 源平均行数 | 33.0 |

近 87% 的 JSON 行是重复样板（同样的 `keep` 数组、`policy` 块、per-node 结构），人需要在 1,251 行里找 1 行；BDD 源平均 33 行，整屏读完。

## 5. 指标 10–12：故障注入与诊断质量（核心差异）

方法：对 **20 个 case × 5 类 JSON 语义故障** 和 **20 case × 3 类 BDD 故障**（另加 20 case × 截断）真实注入后运行对应检查器，记录 exit code、耗时、消息长度、是否含行号。

### 5.1 语义故障（结构合法但含义错）

| 故障 | JSON `validate` 检出 | BDD `transpile --check` 检出 | 诊断样例 |
|---|---:|---:|---|
| 未知 op（`op: no_such_op_xyz`） | **0/20 (0%)** | — | validate 打印整个 spec、exit 0 |
| 悬空边（`edge → ghost_node_xyz`） | **0/20 (0%)** | — | 同上，直到运行才炸 |
| 未知 capability | **0/20 (0%)** | — | 同上 |
| 未知 assertion | **0/20 (0%)** | — | 同上 |
| 缺 `start` | 20/20 (100%) | — | `Error: spec missing 'start'`（唯一抓到的） |
| 未知 step 动词 | — | **20/20 (100%)** | `line 8: noSuchVerbZZZ wait for ...`（带行号） |
| 缺 Scenario 头 | — | **20/20 (100%)** | `feature has no Scenario` |
| Feature 关键字拼错 | — | **20/20 (100%)** | `line 1: text before any Feature: header` |
| **合计** | **20/100 = 20%** | **60/60 = 100%** | — |

### 5.2 语法/截断故障（两边都擅长）

| 故障 | JSON | BDD |
|---|---:|---:|
| 文件截半（EOF 语法错） | 20/20 (100%)，含行号 | 20/20 (100%)，85% 含行号 |
| 平均检查耗时 | 3.1 ms | 3.6 ms |

### 5.3 诊断质量

| 量 | BDD 语义错误 | JSON 截断错误 |
|---|---:|---:|
| 平均消息长度 | 122 字符 | 54 字符 |
| 含行号比例 | **100%** | 100%（仅语法层） |
| 平均检查耗时 | 3.4 ms | 3.1 ms |

**BDD 的错误消息短、带 `file: line:`、直接点名错误 token；JSON `validate` 对语义错误是结构性盲区——`unknown_op` / `dangling_edge` / `unknown_capability` / `unknown_assertion` 四类全部 exit 0，只有运行到那一刻才失败**（与 `bdd compare` 既有的 87 个语义故障注入结论一致：JSON `validate` 抓 0/87，控制组 missing-start 抓 29/29，证明是真盲区而非坏探针）。

## 6. 指标 13：作者侧表达力与词汇门禁

来源：`laya-workflow bdd score`（14 个 authoring 任务；2026-10-14 复核）。

| 量 | 值 |
|---|---|
| expressiveness（intent → 可编译 workflow） | 14/14，coverage 100% |
| 词汇 recall | 143/143（100%） |
| 词汇 precision | 81/81（越界 step 100% 按名拒绝，从未误编译） |
| `@outputs` 契约 mutation 捕获 | 14/14 |
| 平均步数 / 任务 | 18.4（258 步 / 222 unique） |
| naive draft 需修复次数 | 81 次（编译器逐条反馈） |

JSON 侧无等价的「闭合词汇」——作者可写任意 `op`/`capability` 字符串，没有编译期 recall/precision 可言（见 5.1：越界值零检出）。

## 7. 指标 14：版本库摩擦（历史 churn）

来源：本仓库 `git log --numstat`。

| 量 | `.feature` 源 | `dsl/**/*.json` 手写 spec |
|---|---:|---:|
| 涉及 commit 数 | 11 | 76 |
| 累计改动行（+/-） | +1,447 / −35 | +14,974 / −1,701 |
| 平均每 commit 改动 | 135 行 | 219 行 |
| 编译产物是否入库 | 42 个 `.feature` ↔ 42 个 tracked spec（成对） | 手写 spec 即源 |

BDD 行：JSON 行的**十分之一**改动量；JSON spec 的任何全局结构调整（policy 字段重命名等）会放大成百上千行 diff，review 成本直接体现在 churn 上。

## 8. 汇总判定

| 维度 | 胜者 | 置信 |
|---|---|---|
| 体积（作者负担） | **BDD 16–38×** | 高（29 case 全量实测） |
| 修改摩擦 | **BDD 2.8×** | 中（10 case 采样） |
| 机器时延 | 平手（都 <10 ms） | 高（5 重复 × 29 case） |
| 语义故障拦截 | **BDD 100% vs JSON 20%** | 高（各 60–100 次注入） |
| 语法错误诊断 | 平手（都 ~100%） | 高 |
| 诊断可读性 | **BDD**（行号 + 短消息） | 高 |
| 结构噪音 | **BDD**（JSON 87% 重复行、6 层嵌套） | 高 |
| 表达力/词汇门禁 | **BDD**（闭合词汇 recall/precision 可量化） | 高 |
| 版本库 churn | **BDD（1/10 diff 量）** | 中（历史数据非受控实验） |

**JSON DSL 的适用面**：机器生成/程序化组装 workflow、需要 schema 校验对接外部系统时，JSON 仍是正确载体——本报告不主张废除 JSON，而是量化了「**人手维护**同一 workflow 时，BDD 相对 JSON 的成本优势」。编译产物 JSON 由 BDD 单向生成，两者是 source ↔ artifact 关系，不存在二选一。

## 9. 局限

1. **对照口径**：JSON 列 = BDD 编译出的等价 spec（真实产物），而非另找人手写一遍——避免了「不同作者写不同实现」的偏差，但手写 JSON 作者通常会省略可选字段，实际可能比 1,251 行少（但会失去与编译产物的等价性）。
2. **语义故障注入的 JSON 侧**：`validate` 的 20% 检出率 = 只有 `missing_start` 一类结构性检查有效；不代表运行期不会失败——恰恰相反，这 4 类故障全部要到运行期才暴露。
3. **时延**：含进程冷启动，重复 5 次取中位数；不含 Chrome/网络（两者同一 runtime，差异为 0）。
4. **churn 指标**：仓库历史非受控实验，BDD 线更年轻、case 更同质，churn 差距只作方向性参考。
5. **语料**：29 个 web 类 workflow（`_probe` 探针排除）；决策型/路由型 workflow（`dsl/routing` 等）未纳入同一语料对照。
