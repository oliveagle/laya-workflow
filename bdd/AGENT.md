# BDD 维护指南（agent 版）

你是这个仓库的 **BDD 维护者**。`.feature` 是唯一事实来源（single source of
truth）——workflow、测试、生产集成测试全部由它生成。**准确率是最高标准**：宁可
编译失败，也不让一个意思不明确的步骤通过。

## 一、这个方案是什么

```
                         ┌─ workflow  spec/          （laya-workflow JSON，跑真实 Chrome）
bdd/*.feature  ── build ─┼─ 测试      manifest.json    （本地 hermetic，CI 用）
（Gherkin 源）   ──>     └─ 生产集成   it.manifest.json  （@production，外部 base_url）
                          + coverage.json（准确率账本：每步覆盖率 + 未匹配清单）
```

一条命令（accuracy gate 内置）：
```bash
laya-workflow bdd build                     # 本地：编译 + validate + 100% 覆盖
laya-workflow bdd build --assist            # + 词汇表外步骤的 needle 建议
laya-workflow bdd build --profile production \
  --base-url https://app.example.com             # 生产集成测试计划（@production 场景）
laya-workflow bdd run --profile production \
  --base-url https://app.example.com             # 真正执行生产 IT（需要 Chrome/CDP）
laya-workflow bdd compare                        # 离线：BDD vs 手写 JSON 的体积 + 造册门禁
laya-workflow bdd live                           # 实战：29 个真实网站（需要 Chrome）
```

**门禁是硬性的**：词汇表外步骤 = 编译错误（exit 1）；生成的 spec 必须过
`laya-workflow validate`；每 feature 覆盖率必须 100%；选了 0 个场景 = 错误。

## 二、写 / 改 feature 的规则

1. **只用标准词汇表**（`laya-workflow bdd vocabulary-check` 里的规则）。当前支持：
   - 导航/动作：`the browser is ready`、`I am on "<url>"`、`I open/navigate to "<url>"`、
     `I wait for the element "<sel>"`、`I click the element "<sel>"`、
     `I click the element "<sel>" if it is present`、`I type "<text>" into the element "<sel>"`、
     `I select "<v>" in the element "<sel>"`、`I press the key "<key>"`、
     `I run javascript "<expr>"`、`I release the page`。
   - 工作流取值（给 agent 当工具用、产出 collected state，而非 pass/fail）：
     `I extract the text of the element "<sel>" into <key>`、
     `I extract the attribute "<attr>" of the element "<sel>" into <key>`、
     `I extract the page url into <key>`、`I extract the page title into <key>`、
     `I wait until the element "<sel>" becomes visible|invisible|absent|enabled|disabled`。
   - 断言 11 种：`the page title contains` / `the page url contains` /
     `the element ... is visible|absent` / `javascript ... is true|false|equals|contains|equals text` /
     `the saved value "<key>" equals text "<text>"` / `the saved value "<key>" contains text "<text>"`。
   > 做"工作流"（不是测试）时优先用 extract/key/wait_until/click-if-present + state 断言：
   > 它是把没有接口的 UI 变成 agent 可调用工具的主路径。
2. **一个 tag 一行**（Gherkin 解析器一行只认一个 `@tag`）：
   ```
   @production
   @smoke
   Scenario: ...
   ```
3. **外部地址用 `<base_url>`**：`Given I am on "<base_url>/"`——本地 profile 注入
   fixture 服务器地址，生产 profile 注入 `--base-url`。绝不硬编码生产域名。
4. **加新 step 必须先扩词汇表**，再在 feature 里用它：
   `laya-workflow bdd vocabulary-check` 的 `_GIVEN/_WHEN/_THEN` 表加正则 + `_args()` 加参数映射，
   然后 `laya-workflow bdd vocabulary-check` 加一行断言它映射到正确 op。否则
   `laya-workflow bdd build` 会以"unknown step"拒绝——这不是 bug，是门禁。
5. **生产集成测试场景打 `@production`**，只跑真实目标，绝不引用本地 fixture
   （`htmx.html` 这类）。
6. **工作流场景用 `@outputs(<key>, ...)` 声明产物**：它把"这个工作流产出哪些 state key"
   变成编译期合同——`laya-workflow bdd build` 会拒绝"声明了但没有任何 step 产出"的输出。
   每个 `@outputs` 里的 key 必须由某个 `I extract ... into <key>` 产出（或 seed 进
   initial_state）。参考 `bdd/features/workflow_capture.feature` + `bdd/fixtures/app.html`。

## 三、维护循环（每次改动都走）

```bash
# 1. 改 .feature / plugins/bdd/main.rhai
# 2. 本地门禁（编译 / 词汇 / 离线 smoke；check.sh 末段真跑浏览器，无浏览器自动跳过）
laya-workflow bdd build --assist
# 3. 有词汇表外步骤？先看 --assist 的建议（带置信度），
#    把可接受的规则写进 plugins/bdd/main.rhai，再重跑。建议永远不直接编译。
# 4. 真跑浏览器（有 Chrome 的机器）：
laya-workflow bdd run           # 无浏览器时打印 skipped 并 exit 0；--require-browser 则改判 error
scripts/bdd/check.sh            # 或 scripts/verify.sh：编译 + 离线 smoke + 浏览器真跑（无浏览器自动跳过）
# 5. 生产 IT（可选，有部署目标时）
laya-workflow bdd build --profile production --base-url <real>
laya-workflow bdd run --profile production --base-url <real>
```

## 四、准确率策略（为什么这样分）

- **确定性编译器 = 100% 精度**：step 正则 → op/assertion/参数，0ms，无歧义。
  一切能靠规则表达的步骤都走这里。
- **needle 只做"建议"**：`--assist` 对词汇表外步骤跑端上小模型（多工具+triggers），
  打印 `op + 置信度`，`≥0.5` 标 LIKELY、`<0.5` 标 guess。它**绝不自动编译**——
  研究（`docs/bdd_to_needle.md`）实测：基础模型对生造措辞全字段准确率约 40%、
  只有 ~10% 过 0.1 置信度 floor，所以建议只是给 agent 的一个输入，最终以
  `plugins/bdd/main.rhai` 里的确定规则为准。
- **validate 双保险**：build 生成的每个 spec 都跑真实 `laya-workflow validate`，
  结构不合法即失败。

## 五、常见错误 → 正确动作

| 报错 | 含义 | 动作 |
|---|---|---|
| `unknown then step: '...'` | 词汇表不认这个 step | 用 `--assist` 看建议 → 加 `plugins/bdd/main.rhai` 规则 |
| `step coverage 40% < 100%` | feature 里有未匹配步骤 | 同上，或改写成标准措辞 |
| `no @production scenarios selected` | 生产计划为空 | 给场景加 `@production` tag |
| `--profile production needs --base-url` | 生产没给目标 | 传 `--base-url` 或设 `$BDD_BASE_URL` |
| `validate rejected the generated spec` | 生成的 spec 结构不合法 | 改 feature 让它编译出合法图 |

## 六、目录速查

> **隔离原则**：BDD 源与 JSON 完全隔离在两个根目录——所有 `.feature` 源在 `bdd/workflows/<类别>/`（层级镜像 `dsl/`），所有 JSON 工件在 `dsl/` + `bench/`。浏览器 feature 的侧车配置 `<name>.config.json` 归入 json 树（`dsl/browser/`），authoring 造册/args 门禁等工具数据归入 `bench/bdd/`。因此 **`bdd/` 内 0 个 `.json`**（含 bench/args_probes），`dsl/` 内 0 个 `.feature`。BDD 是源、JSON 是编译产物（单向生成）。这条隔离现在由门禁**机器化**（P44）：`dsl smoke` 末尾内置 `isolation_audit` 并作为回归 `bdd-json-isolation`，见下方「bdd/json 两树隔离不变量」。

- `bdd/features/*.feature` — 正式场景（CI 门禁的 glob）
- `bdd/features/setup/` — `include:` 拉入的步骤列表（无 Feature 头）
- `bdd/workflows/` — 全部 BDD workflow 源（单一层级，镜像 `dsl/`）：`browser/`（29 实战站点 live 语料 + `_probe`）、`examples/`、`tasks/`、`routing/`、`agents/`（决策图 `@decision` 类别，随转换持续扩展）
- `bdd/fixtures/` — 本地 hermetic 夹具页（`app.html` 是"无接口 UI 转工作流"的示例目标）
- `bdd/features/workflow_capture.feature` — 工作流语义的端到端示例（extract/key/wait_until/条件点击/@outputs）
- `laya-workflow bdd vocabulary-check` — 词汇表（step → op/assertion）
- `laya-workflow bdd transpile` — 编译器（Gherkin → spec）
- `laya-workflow bdd build` — 统一 accuracy gate + 多产物（本指南的核心命令）
- `laya-workflow bdd run` — 执行器（本地 hermetic / 生产 IT）；无浏览器时 skip（exit 0），`--require-browser` 改判 error，`LAYA_BDD_SKIP_BROWSER=1` 关掉 `check.sh` 里的这一段
- `laya-workflow bdd build --assist` — needle 建议模块（只建议，不编译）
- `bench/bdd/` — bdd 工具链 JSON 数据（authoring 造册 `tasks/*.json`、实战结果 `live/`、`args_probes.json`、跨仓端口来源封存 `port_pins/<cat>.json`）；`bdd/` 内无任何 `.json`
- `bench/bdd/live/REPORT.md` — 实战结果（29 passed / 842 steps）+ BDD vs 手写 JSON 效率对比
- `laya-workflow bdd live` — 跑实战语料（需要 Chrome，**绝不在 CI**）
- `laya-workflow bdd compare` — BDD vs 手写 JSON 的体积/门禁对比（离线，可进 CI）
- `laya-workflow bdd port-check [--pin <seal>] [--sources <dir>]` — 跨仓转换闭合性（每个上游 scenario 都有 BDD 端口、每个端口都有上游来源）。上游语料在另一个 repo，故来源**名集**封存在 `bench/bdd/port_pins/<cat>.json`（check-in 的是「只有名、`fingerprint` 留空」的 seal，不引用他仓任何字节或其哈希）：`--pin` 无需第二份 checkout 即可证明闭合，`check.sh` 默认就跑这一半；`--sources` 指向活的 ole-eval `code/qwen_vm/app_scenarios` 时把 seal 也拉上审判席（活名集必须与 seal 相同、seal 里带指纹的项必须仍匹配），`LAYA_OLE_EVAL_SOURCES` 设了才跑；`--write-pin` 是本地重新封存（审阅后的动作，不是门禁）
- `laya-workflow bdd import <spec.json> [--out <f.feature> | --into <cat>]` / `laya-workflow bdd import --dir <DIR> [--out <dir> | --into <cat>] [--json <f>] [--force]` — 正向搬运：把已有 workflow spec 转成 `@decision` `.feature`（transpile 的逆）。单文件默认打 stdout；`--into` 归入本仓 `bdd/workflows/<cat>/` 并把 spec 抄进 `dsl/<cat>/`（`name` 钉成端口名，保证落仓即过 `round-trip`/`import-check`）。`--dir` 递归批量：只收「解析成功且 `nodes` 非空」的 json，按名跳过 `*.config.json`、其余非 workflow json 记为 skipped，**一个都没命中即报错**（绝不 false-green）；每个 feature 落盘前先验证「重新解析 + 重新编译 == 原 spec（`same_graph`）」；目标已存在默认报冲突（`--force` 覆盖）。`bdd import-check` 门禁证明每个已入库 spec 都能被 import 出的 feature 编译回同一张图（`check.sh` 真跑）

- `laya-workflow bdd features-check` — 语料完备性门禁：`bdd/` 下**每一个** checked-in `.feature` 都必须能编译，且必须落在某个已登记的门禁桶里（`features` / `browser` / `decision` / `tasks` / `examples`；`bdd/features/setup/` 是 `include:` 进来的步骤清单，不是 feature，跳过）。起因：`bdd/workflows/examples/`（`docs/bdd_quickstart.md` 让新作者照抄的两个 feature，如 `bdd/workflows/examples/login_smoke.feature`）此前**没有任何门禁读它** —— 一次词汇表改动就能让一个「文档里的例子」悄悄坏掉，而所有检查依旧全绿。这个门禁把它们一起编译（用的就是 `bdd build` 的编译器），并把任何「落在没人编译的目录里」的 `.feature` **点名**，而不是让它未经校验地入库。`check.sh` 真跑
- `laya-workflow bdd live-decisions [--base-url <url>] [--filter <sub>] [--json <file>]` — 决策语料的 **live 结构门禁**（P133/P134）：把全部 `@decision` feature 的注册样本状态（`bench/dsl_smoke_states.json`）过真实 System-1 后端（默认 `$BDD_BASE_URL`，否则已部署的决策服务 `:18405`），门禁只问**结构**：编译/校验通过 + 每个状态 **in-contract 终止** + 0 backend/contract 错误；**label 与离线期望的一致率只打印、不作门禁**（live 模型的 label 本应大多与启发式离线期望不同）。**「返回」不等于「终止」**（P134）：`ResilientWorkflow::run` 在 `max_iterations` / `error_node_missing` 这种安全阀上也返回 `Ok`，故引入纯函数 `walk_outcome_clean(final_action)`，不终止即记 `states_nonterminating` 并使该 spec 失败；引擎的 3 次重访守卫（`loop_detected`）只作信息计数（`iterative_refine_loop` 这类故意循环的图会触发）。需要 live 模型，故**不进**离线 `check.sh`；回归 `laya-workflow-tests bdd-live-decisions`（14/14）。
- `laya-workflow bdd app-parity [--json <file>]` — 内置 app 端口一致性门禁（P137）：把 `laya-workflow apps` 的 32 个参考用例（4 个内置 app 的 `src/apps.rs::all_reference_cases` 8+5+6+6，加组合 `gateway` 的 `gateway_reference_cases` 7）逐个喂给该 app 的 checked-in BDD 端口 spec、走真实引擎（离线 `HeuristicBackend`），要求投影 label 命中期望（`|` 备选）；任何不符即 FAIL 并点名 app / 端口 / 输入 / 期望 / 实得。端口是 app 路由的**数据**重述，故这是「app 为**代码**、端口为**数据**」时二者逐条一致的可测证明。组合 `gateway` 的 app 把裁决写在 `action`、端口写在 `label`，故门禁**同时**驱动 app 与端口、要求两者都命中（P138）。离线、无 Chrome、无模型，故进 `scripts/bdd/check.sh`；回归 `laya-workflow-tests bdd-app-parity`。

## 七、决策 workflow（@decision）—— agentic 决策图的 BDD 写法

> 这是把 **agentic 决策 workflow** 变成 BDD 的主路径（也是把 `dsl/<cat>/<name>.json`
> 里 99 个决策 spec 全量转成 `.feature` 的做法）。一条 `@decision` feature = 一张决策图：
> **Feature = 整张图，每个 Scenario = 一个决策节点**。编译产物是决策图 spec
> （`nodes/start/max_iterations/policy/capabilities`），不是浏览器步骤 spec。

### 文件放哪 / 来源

- **绿场起点**：`laya-workflow bdd scaffold --name <wf> --cat <cat> --intent "<intent>"`
  一条命令开出最小合法 `@decision` 骨架（自带 authoring 词汇注释、自验证能过 `bdd build`）。
  默认是**典型两节点图**（choice → score → STOP，带 threshold label + copy_keys 节点），
  复制 Scenario 加节点、改 edge 即可长成真实多节点 workflow；`--single` 退化为单节点起点；
  `--nested` 开 prefilter → 子工作流 → audit 管线起点；`--pattern gate` 开单节点门禁骨架
  （choice → `Then gate "<q>" on option "B" with block 0.6 allow 0.7`，适合风险/审批）；
  `--pattern loop` 开迭代精修自环（Background `at most N iterations` + verdict 节点
  `revise` 回自身 + `allow up to 3 retries`）；`--pattern` 取值见 `bdd scaffold --help`；
  `--stdout` 只打印不写文件，重复写需 `--force`
- 源：`bdd/workflows/<cat>/<name>.feature`（层级镜像 `dsl/<cat>/`，如 routing/、agents/、capabilities/…）
- 编译产物：`dsl/<cat>/<name>.json` —— **这是权威 spec，由 `bdd round-trip` 证明等价，不许手改**
- 门禁：`laya-workflow bdd round-trip` —— 每个 `@decision` feature 必须逐字段复现其 dsl spec；
  **反向完整性**：任何有 dsl spec 但没有 `@decision` 源的，round-trip 直接 FAIL（"convert it"）。

### 结构：Feature = 图，Scenario = 节点

```gherkin
@decision
Feature: support_ticket_router

  Background:                        # 整张图的设置（可选）
    Given the workflow runs at most 20 iterations

  Scenario: classify                 # 一个决策节点
    Given a choice question "category" asks "Which team should handle this ticket?"
      | answer    | meaning          |   # choice 表：第一行是表头 | answer | meaning |
      | billing   | invoices, ...    |   # 其余行是 criteria
    When the answer "technical" goes to "severity_probe"   # edge 条件 → 目标节点
    And any other answer goes to "STOP"                    # edge 默认
    Then keep the answer to "category"                     # copy_keys
    And require confidence at least 0.4                    # min_confidence
    And allow up to 3 retries                              # max_retries

  Scenario: severity_probe           # 第二个节点
    Given a score question "severity" asks "How severe is the impact?"
      | level    |                   # score 表：| level |（criteria 是 level 列表）
    When any other answer goes to "STOP"
    Then label "PAGE_ONCALL" when "severity" is at least 1.5   # 有序 threshold 规则
    And label "BACKLOG" otherwise                               # 兜底
```

### 决策词汇表（Given / When / Then）

**Background（整图级）**：`Given the workflow runs at most N iterations`（max_iterations）、
`Given the policy`（| key | value | 表 → policy 块）、`Given the capabilities`（| name | config-JSON | 表）。

**Given 问题（每节点 ≥1 个问题）**：
- `a choice question "Q" asks "..."` + `| answer | meaning |` 表
- `a score question "Q" asks "..."` + `| level |` 表
- `a noul question "Q" asks "..."` + 可选 `| truthy | ... |` / `| falsy | ... |` 表
- `the sub workflow "NAME"` —— 节点只引子工作流（不能混节点内容）
- `And when the sub workflow completes continue at "NODE"` —— 子工作流完成后的**交接点**：子内部 STOP 边被重定向到调用方节点（P25；参考 `bdd/workflows/pipelines/intake_pipeline_nested.feature`）
- 启发式（跟在问题后、配置**最近一个**问题）：
  - `answer "X" when the field "F" contains <needles> with hit N [and miss M]`（field_any）
  - `answer "X" when the text contains <needles> with hit N [and miss M]`（any）
  - `score "X" from the numeric field "F" [with miss M]`（numeric）
  - `answer "X" when the field "F" matches <patterns> with hit N [and miss M]`（regex）
  - `answer "X" with mid N when the field "F" contains <needles>`（mid）
  - `answer by rules on the field "F" with hit N [and fallback "X"]`（match_rules + | label | needles | 表）
  - `score "X" when the field "F" contains "HIGH" scoring H and "MID" scoring M miss L`（score_bands）
  - `the answer is always "X"`、`the answer comes from the field "F"`

**When 边**：`the answer "X" goes to "NODE"`（edge 条件）、`any other answer goes to "NODE"`（默认）。

**Then 动作**：
- 阈值规则（**有序**，round-trip 断言顺序）：`label "L" when the answer to "Q" is "X"` /
  `... is one of "X","Y"` / `... when the answer is "X"`（implicit）/ `... with at least C confidence` /
  `label "L" when "Q" is at least N` / `label "L" when "Q" is below N` / `label "L" otherwise`；
  **合取**：把任意两个叶子条件用 ` and ` 连起来（`label "L" when <cond> and <cond>`，
  如 `label "PAGER_BILLING" when the answer to "category" is "billing" and "urgency" is at least 1.5`），
  编译成 `{"all": [...]}`（每个叶子仍可各自点名 `question`）。用于「两个信号同时成立」的场景。
- state：`keep the answer to "Q"`（copy_keys）、`keep the state key "K"`
- 节点设置：`the primary question is "Q"`、`the action reads the question "Q"`、
  `require confidence at least N`、`allow up to N retries`
- 能力调用：`call the capability "NAME"` + `| with.<k> | ... |` / `| chain.<as>.capability | ... |` 表
- 高级动作：`gate "Q" on option "O" with block B allow A`、`merge open probabilities on "Q"`、
  `combine "C" with signal "S" fallback "F" review "R" requiring MIN high H low L`、
  `rubric "Q1" at L1 levels weight W1 and "Q2" at L2 levels weight W2 requiring M`、
  `prepare a UI proposal from operation "OP" field "F" amount "A" surface "S" hash "H" requiring M [value "K"]`

> 单元格里要写字面 `|`（如 shell 管道）时转义成 `\|`；JSON 值里的 `\r\n` 等按 JSON 转义。

### 正确性 & 行为门禁（决策路径怎么被证明对）

- **节点 `state` 投影必须说它做的（P142，正确性/易用性）**：`project_state` 只读 `{"keep": [<state key>…], "rename": {<out>: <state key>}}`；其余一切形状——非对象的 `state`、`keep` 不是字符串数组、`rename` 不是 string→string 映射、**不认识的键**（拼错的 `keeep`/`renmae`）、以及既不声明 `keep` 也不声明 `rename` 的 `state` 对象——都会被**静默忽略**，于是节点把**整份 state** 发给后端：一个从不投影的「投影」。这和 P139/P141 同类——`validate` 必须拒绝只能悄悄违背声明意图的形状。现在 `validate_graph_semantics` 逐节点拒（带 JSON 种类与 `suggest` 拼写建议）。**`keep: []` 仍合法**（编译器「无保留键」的编码，等价于不投影）。**编译器不受影响**（`compile_decision_node` 只在非空时吐 `state`；browser `node()` 永远带 keep 键），163 语料零回归。另外 `bdd import` 对 `state.rename` **大声拒绝**（feature 语言暂无对应步骤）——此前「keep + rename」会被静默丢弃，重编译后发给后端的键集与源 spec 不同。回归 `laya-workflow-tests validate-state-contract`（14 断言：九负 + 五正）、`bdd-import`（+2：rename 被拒 / 纯 keep 仍导入）。
- **节点 `state` 投影的 `rename` 表达力（P143，正确性/核心化）**：P142 让 `validate` 接受 `state.rename`，但 feature 语言**没有 rename 步骤**，于是 `bdd import` 只能**大声拒绝**（再早是静默丢弃）。现在补上这一步：`Then map the state key "<out>" from "<in>"`（编译成 `state.rename`）—— `compile_decision_node` 在 `keep` 或 `rename` 任一非空时吐 `state`，`bdd import` 对 `keep`/`rename` 都逐条回吐（serde_json 键有序，feature 稳定）。于是「任意已知 workflow ↔ BDD」对**整个 `state` 投影**闭合：`json {keep,rename} → bdd import → bdd transpile` 的 `state` 逐字段相同（实测）。词表 `decision_templates()` 补该模板、`dec_then_table()` 补该正则+tag，`decision-vocab-check` 由 42/42 变 **43/43**（then=23）。回归 `bdd-import`：rename 投影 → 产出 `map the state key "out" from "a"` 步骤 → 重编译 `state` 不变（P142 那条「rename 被拒」的断言随之改为「round-trip」）。**诚实边界**：`rename` 的键顺序来自 serde_json 的 BTreeMap（稳定），非源 spec 的声明顺序。
- **`state` 投影的运行期语义（P144，正确性/核心化）**：P142 只堵**静态**形状，运行期还剩一洞——`project_state` 末尾 `if out.is_empty() { state.clone() }`：节点声明 `keep: ["request_id", …]` 而运行态里这些键一个不存在时，投影**匹配不到任何键 → 静默回落整份 state**，「只保留 X」变成「把全部键（含 secret / 无关 blob）发给后端」。这正是 `dsl/ole_eval` 语料的实况：离线启发式后端从**整份 state** 取答案（命名 handler 扫文本 / `heuristic.answer_field` 读字段），而语料的 `keep` 多为装饰（`request_id`/`actor_id` 在注册态里并不存在），一直接着 fail-open 才跑得过去。P144 三处收口：① `project_state` 不再回落——**声明 ≥1 键却零命中 → `{}`（fail-closed）**；零声明的（`state` 缺失/null 或 `{"keep": []}` 编码）仍恒等。② `node_from_spec_with` 把每题 `heuristic.answer_field` 折进 `keep`——节点必须看见它读的键（`criteria.from_state` 由引擎在投影**之前**从原始 state 展开，故不折）。③ 对**真读整份 state** 的 5 个 `threshold` 节点（adaptive_risk_control / aml_screener / content_safety_guard / deployment_canary_guard / intrusion_signal_guard），删掉那条从不命中的装饰 `state.keep`——不声明投影 = 整份 state = 它真正的语义。回归 `laya-workflow-tests spec-state-projection-runtime`（13 断言）。**诚实边界**：运行期收紧（`state_fn` 返回 `Value` 非 `Result`，此处无法报错）；投影只影响**后端可见 state**，动作/断言读原始 state。**遗留**：语料其余节点的 `keep` 仍是「声明 ∪ 读键」，读键由运行期折入，未逐一改写为自描述。
- **节点 / edge 的未知键必须被拒（P145，正确性/易用性）**：`node_from_spec_with` 只读节点的 `name`/`questions`/`edge`/`min_confidence`/`primary_q`/`max_retries`/`state`/`action`（引用节点再加 `workflow`），edge 只读 `condition`/`default`/`min_confidence`；**其余任何键**——把 `questions` 拼成 `questoins`、`action` 拼成 `actoin`、edge 上多一个 `condtion`——解析器与引擎**从不读它**，于是 `bdd build` 过、`validate` 也过，但节点声明的**问题 / 动作 / 路由被静默删掉**：一个节点能在一路绿灯下失去它本该有的行为。这与 P142（`state` 里认错键 → 静默**放大**成整份 state）同族，只是这里静默**删除**而非静默**放大**。现在 `validate_graph_semantics` 逐节点、逐 edge 拒未知键，并带 `suggest` 拼写建议（`node a: unrecognised key "actoin" (did you mean "action"?)`）。唯一例外是**派生键** `has_action`（`describe`/round-trip 会产出它）：它被**接受，但必须与 `action` 的存在一致**——`has_action: true` 而节点没有 `action`（或反之 / 非布尔）都拒，于是这条派生键也从「装饰」变成「被对账的不变量」。编译器 / `bdd import` 只吐已知键，语料零回归；顺带修掉一处**测试自身**的静默忽略键（inline 嵌套用例的引用节点写了 `edge_default`，而引擎只认 `edge.default`）。回归 `laya-workflow-tests validate-node-keys`（13 断言：五正 + 八负）。
- **问题对象 / heuristic 的未知键必须被拒（P146，正确性/易用性）**：P145 收了**节点对象**与**其 edge 对象**的未知键，但**更深一层**仍敞着 —— `questions.<id>` 只读 `type` / `instructions` / `criteria` / `heuristic`（规则引擎另读 `violating` / `violating_from`），`heuristic` 只读一组离线后端键（`answer_field` / `field` / `extract_numeric` / `match_any` / `match_mid_any` / `match_regex` / `match_rules` / `fallback` / `answer` / `p_*` / `score_*`）；**其余任何键**（`critera` / `answer_feild` / `matc_any`）解析器与引擎从不读，于是 `validate` 一路绿灯、而问题的**选项集 / 离线读出口**被静默删掉 —— 与 P145 同族，只是再深一层（P145 删节点 / edge 键，这里删问题 / 启发式键）。现在 `validate_graph_semantics` 逐题拒未知问题键、逐题拒未知 `heuristic` 键，带 `suggest` 拼写建议。**派生键** `truthy` / `falsy`（编译器 `noul` 注解）与 `answer`（编译器 `heur_answer` 步，`bdd import` 会回吐）被接受，同 P145 的 `has_action`。编译器 / `bdd import` 只吐已知键、语料零回归；顺带修掉一处**测试自身**的静默忽略键（`test_validate_action_question_type` 的 `score` 问题写了引擎从不读的 `levels` —— rubric 的 `dimensions[].levels` 是**另一个对象** —— 改为 `criteria` 列表）。回归 `validate-question-keys`（9 断言：四正 + 五负）。
- **动作对象 / 其嵌套对象的未知键必须被拒（P147，正确性/易用性）**：P145 收节点 / edge、P146 收问题 / heuristic，**再深一层**是 `action` 对象本身与其嵌套对象 —— `run_action` / `run_call_action` 只按名读下面这些键，其余（`capabilty` / `rulez` / `dimenions` / `wieght`）解析器与引擎从不读，于是 `validate` 一路绿灯、而动作**静默丢掉它的能力 / 规则 / 维度**。现在 `validate_graph_semantics` 逐 action 按 kind 校验 key 集（`none` / `merge_open_probs` 无；`copy_keys` = {keys}；`threshold` = {rules}；`rubric` = {dimensions, min_confidence}；`combine` = {choice, signal, min_confidence, fallback, review_label, high_threshold, low_threshold}；`gate` = {option, block_at, allow_at}；`ui_proposal` = {operation, field, amount, min_confidence, surface, snapshot_hash, value_key}；`call` = {capability, with, chain, project}；公共 `kind` / `question`），并逐 `rules[]` = {when, label}、逐 `dimensions[]` = {question, levels, weight}、逐 `chain[]` = {capability, as, with, project} 校验，未知键带 `suggest` 拼写建议。**顺带把两处「声明了却被忽略」的键变成「声明即生效」**（白名单必须诚实）：① `ui_proposal.surface` / `snapshot_hash` 现在按声明的**状态键名**读取（默认仍是 `surface` / `snapshot_hash`，语料逐字节不变）；② `chain[]` 步的 `project` 现在真的按指针投影该步结果（与主 `call` 同 `body` 回退）。编译器 / `bdd import` 只吐已知键、语料零回归。回归 `validate-action-keys`（9 断言：四正 + 五负）+ 2 条行为断言。
- **spec 顶层 / `policy` / `_bdd` 的未知键必须被拒（P148，正确性/易用性）**：把 P142（`state` 对象）、P145–P147（节点/edge、问题/heuristic、动作）的「未知键静默忽略」收口推到**最外层** —— spec 顶层只读 `name` / `dsl_version` / `description` / `start` / `nodes` / `max_iterations` / `convergence_window` / `convergence_eps` / `capabilities` / `policy` / `_bdd`，`policy` 只读 `allow_exec` / `allow_hosts` / `allow_paths` / `max_timeout_ms` / `max_output` / `retries`，`_bdd` 是编译器元数据（`feature` / `feature_path` / `mode` / `scenario` / `tags` / `initial_state` / `outputs`）。**其余任何键**（`satrt` / `policiy` / `allow_exex`）解析器与引擎从不读 —— 于是把 `start` 拼成 `satrt` 后 `validate` 仍绿、工作流却从默认处起跑，`policy` 拼错则整份策略**从不生效**。现在新增 `validate_spec_keys`，在 `from_spec_with_dir_cycle` 入口（含嵌套子 spec）逐顶层 / 逐 `policy` / 逐 `_bdd` 键拒未知键 + `suggest`；非对象 `policy` 也拒（否则整份策略被静默忽略）。编译器 / `bdd import` 只吐已知键、语料（`dsl/` + `bench/`）零回归。回归 `validate-spec-keys`（7 断言：三正 + 四负）。
- **capability 定义对象必须可运行（P149，正确性/易用性）**：P128 拒了「声明了却从不读的 option」，但**同一个定义对象**还有另一半洞 —— 一个 kind 的**必备 target 字段缺失**时，`validate` 仍绿、却永远跑不起来：`rpc` 少了 `url`、`s3` 少了 `endpoint`/`bucket`、`tcp`/`udp` 少了 `host`/`port`、`sqlite` 少了 `db`、`sql` 少了 `dsn`、`web_search` 少了 `endpoint`、`kafka` 少了 `url`、`agent`/`mcp` 少了 `url`（http）或 `command`（stdio）、`mcp` 少了 `tool`。运行时只把配置串当作模板 `expand`（空模板仍是空），所以「空」永远补不回来 —— 每次调用都会 bail `<kind> needs …`（P139/P140「validate 蕴含可运行」在 capability 层的同族）。现在 `parse_cap` 新增 `check_required_options`，按 kind 拒这些缺失字段（`mcp`/`agent` 按 transport 判 `url` / `command`）。**边界**：凡运行时允许调用方用 `with` 补的字段（`graphql.query`、`kafka.topic`、`pdf.path`、`archive.path`、`db.sqlite`、`cron.expr`、`computer_use.allowed_surface`）**不**在此列 —— 那种 capability 经 `with` 仍可跑。语料零回归（全仓 193 spec 扫过，各 kind 的必备字段 100% 提供）。回归 `validate-capability-runnable`（21 断言）。
- **capability 选项的取值必须有合法值域（P150，正确性/易用性）**：P128 拒了「声明了却从不读的 option」、P149 拒了「必备字段缺失」，但**已声明 option 的取值**从未被校验 —— 解析器把 `max_bytes`/`max_events`/`max_operations`/`max_output`/`max_owned_pages`/`max_results`/`max_text`/`max_tokens`/`owned_idle_ms`/`startup_timeout_ms`/`timeout_ms` 读成 `u64`、`chars_per_token`/`min_confidence`/`temperature` 读成 `f64`、`port` 读成 `u16`，非数或越界时**静默回落默认值**（`-1`、`1.5`、`"9000"`、`true` 全被 `as_u64` 丢弃；`port: 70000` 被 `as u16` **回绕成 4464**）——`validate` 仍绿、运行期却按默认值跑。修法：`parse_cap` 末尾新增 `check_option_domains`，对 `U64_OPTIONS` 要求 `as_u64`、`F64_OPTIONS` 要求 `as_f64`、`PORT_KINDS`（tcp/udp/redis/nats/mqtt/smtp/mail_send）的 `port` 要求 `1..=65535`，错误信息解释「会被静默替换成默认 / 端口会回绕」。语料零回归（全仓 spec 扫描 0 违规）；回归 `validate-option-domains`（15 断言：六正 + 六负 + 三消息）。
- **capability 字符串选项的闭集取值（P151，正确性/易用性）**：P128（不读的键）/P149（缺 target 字段）/P150（数值域）之后，「声明了引擎却永远接受不了的值」还剩最后一面 —— 运行时按**闭集**分派的字符串 option：`op`/`mode`/`driver`/`format`/`transport`/`channel`/`method`/`hash`。一个集合外的值永远不会被兑现：调用要么 `bail`（`text op "len" unsupported …`）、要么被**静默替换成默认**。`validate` 现在拒绝它（`parse_cap` 末尾的 `check_option_values`，覆盖全部相关 kind 的闭集，并折合 `md`/`tokens`/`kv`/`database`/`computer-use`/`notify_local` 等别名）；空串按**引擎自身**的处理镜像（`allow_empty`：`db.op ""`→query 放行、`text.op ""`（会 bail）拒绝）；非字符串值也拒（同 P150 对数值的处理）。语料零违规（全仓 spec 扫描）；回归 `validate-option-values`（49 断言）。顺带把 5 个旧测试改到**解析期**拒绝（datetime/text/json/hash 的 bad op、sql 的 bad driver）。
- **capability 布尔/静默回落选项的取值（P152，正确性）**：P128（不读的键）/P149（缺 target 字段）/P150（数值域）/P151（闭集字符串）之后，「声明了引擎却永远兑现不了的值」还剩两类：① 解析器用 `as_bool` 读的布尔 option —— `http.expect_json`/`allow_error_status`、`sqlite`/`db.readonly`、`csv.headers`、`notify.bell`/`timestamp`、`browser.launch`/`attach`/`human`、`web_fetch.body_urls_array`：一个非布尔值（`"false"`、`0`、`"yes"`）被 `as_bool` **静默丢弃**、回落默认值（经典 `"false"` 当真值）；② 三个**静默回落**的字符串 option —— `pdf.op` 集合外 → `text`、`web_fetch.format` → `text`、`web_search.method` → `GET`（运行时走 `_ => 默认` 而不 bail），拼错的值**跑完全程却行为错**。修法：`check_option_domains` 新增布尔表 `BOOL_OPTIONS`（按 kind 判，`csv.headers` 在 csv 是布尔、别处是对象），`CLOSED_SETS` 升为五元组加 `fallback: Option<&str>`，`check_option_values` 对 `Some(fb)` 发一条区别于 bail 的「静默回落」错误。语料零回归（全仓 spec 扫描 0 违规）；回归 `laya-workflow-tests validate-option-values-2`（26 断言：八布尔正 + 四闭集正 + 七布尔负 + 三回落负 + 四条消息断言）。**诚实边界**：`i64` option（`offset_secs`/`ttl_secs`/`id`）不在此列（JSON `3` 是合法 `i64`，不是干净的 bug 类）；`suggest` 对**换位**拼写（`satrt`↔`start`）不给提示（错误信息仍点名键）。
- **capability 逗号列表 / 定长字符 / 闭集 runner 的取值（P153，正确性）**：P128–P152 把 capability option 的「键 / 必备字段 / 数值域 / 闭集字符串 / 布尔类型 / 静默回落」逐层收口后，同一「声明了引擎却兑现不了的值」还剩三处：① `metrics.what`（别名 `sysinfo`）是**逗号分隔**的固定词表 `mem/load/uptime/cpu/disk`，运行时按 `,` 切分后 `want.contains(&tok)`，一个未知 token（`momery`/`cupy`）**静默落空** —— `validate` 绿、结果里就是缺你要的那项（实测 `what:"momery"` → 结果只剩 `{"capability":"metrics"}`）；② `csv.delimiter` 由 `chars().next()` 读取，多字符串（`"||"`）被**静默截断成首字符**（实测 `delimiter:"||"` 把 `a||b||c` 切成 `["a","","b","","c"]`）；③ `goal_runner.runner`（别名 `agent_goal`）是固定两值 `cxgo/cmdgo`，未知名在运行期 `resolve_runner` **bail**。修法：`check_option_domains` 增 `metrics.what` 逐 token 校验（空串=默认放行、按 `,` trim）+ `csv.delimiter` 单字符校验（>1 字符拒，报「只保留首字符」），`CLOSED_SETS` 补 `("goal_runner","runner",["cxgo","cmdgo"],true,None)`，`canon_kind` 补 `sysinfo→metrics` / `agent_goal→goal_runner`。语料 0 违规；回归 `laya-workflow-tests validate-option-values-3`（28 断言：十四正 + 八负 + 二类型 + 四消息）。**诚实边界**：`metrics.disk_path`（路径，非闭集）、`file.allow_roots`（依赖 `policy`）仍未纳入。
- **capability 字符串数组 / 对象型选项的元素取值（P154，正确性）**：P128–P153 之后，「声明了引擎却兑现不了的值」最后还剩两面 —— 解析器按 `Vec<String>` 读的**字符串数组**选项（`exec.argv` / `agent.command` / `mcp.command` / `goal_runner.args` / `file.allow_roots` / `computer_use.allowed_fields`）用 `filter_map(|x| x.as_str())` **只留字符串元素**：一个非字符串元素（未加引号的数字 `"--max-turns", 8` / bool / null）被**静默丢弃**，命令少跑一个参数；非数组值则整个列表丢失（实测 `exec argv:["echo","A",5,"B"]` → 运行输出 `A B`，那个 `5` 没了）。按 `as_object` 读的**对象型**选项（各 kind 的 `headers`、`exec.env`）遇非对象值**整份 map 静默丢弃**。修法：`check_option_domains` 新增两张表 `STRING_ARRAY_OPTIONS`（按 kind）逐元素验字符串、`OBJECT_OPTIONS`（按 kind）验对象，`canon_kind` 补 `object_store→s3`（`app_server`/`computer-use`/`agent_goal`/`search`/`fetch_url` 已折）。语料 0 违规（366 个 json 扫过）；回归 `laya-workflow-tests validate-option-values-4`（27 断言：十一正 + 十二负 + 四消息）。**诚实边界**：`headers`/`env` 的**值**（模板串）不校验类型；`plugin` 多形态身份、`sqlite`+`db` 的 op 一致性仍未纳入。

- **“did you mean” 的换位拼写（P155，易用性/正确性）**：`suggest` 的度量是 bigram Dice + 最长公共前缀加成，对**相邻换位**型拼写有盲区 —— `satrt`↔`start` 只共享一个相邻 bigram（`rt`），得分 0.32 < 0.5 阈值，验证错误因此**不给提示**（即 P152 记录的诚实边界）。修法：`str_similarity` 在 Dice+LCP 之外**并列**一条归一化 OSA（Damerau-Levenshtein，仅允许相邻换位）编辑相似度 `1 - osa/max_len`，取两者较大值 —— 换位被当作 1 次编辑（`satrt`→0.80、`strat`→0.80），`id_keey`→`id_key` 等仍由 bigram 命中。**“取较大”是关键**：新项只可能**新增**提示，绝不抹掉 bigram 已给出的提示，故既有 8 条 `spec-closest-match` 断言全部原样通过。误报零回归：`complete`↔`billing/shipping`（0.125）、`is_risky`↔`is_safe`（0.465 < 0.5）仍不出提示。回归 `laya-workflow-tests spec-closest-match`（13 断言：原 8 + 换位 2 + 插入 1 + 远邻换位 1 + 对称/上界 2）。**诚实边界**：度量仍是 best-effort 提示，从不 gate 构建；阈值 0.5 下的 OSA 项等价于「编辑距离 ≤ 长度一半」，极短标识符（1–2 字符）仍可能被换位项拉到 0.5。

- **`plugin` capability 的三选一身份至少要有一种（P156，正确性）**：`kind: plugin|script` 的插件身份由三者之一给出 —— `plugin`/`name`（搜索层 id）、`dir`（显式路径）、脚本 `entry`；`load_sources` 至少要有一个，三者全无时引擎无从加载，每次调用 bail `plugin capability needs 'plugin' (a name), 'dir', or a script 'entry'` —— 而 `validate` 仍绿（这是 P149「capability 必须可运行」的插件姊妹面，此前未纳入）。修法：`check_required_options` 新增 `plugin|script` 分支，`plugin`/`name`/`dir`/`entry` 四者全为空（缺失或仅空白）即拒，错误点名三种身份与运行期 bail。**只判身份存在性**：不查插件能否真的解析到（搜索层含 `$LAYA_PLUGIN_DIR`、`plugins/`、`websites/*/plugin/` 与内置，随主机而变，离线无法判定 —— 这是有意的边界），`dir` 指向的路径是否存在也不查（依赖 spec root）。语料零违规（每个 plugin cap 都带 `plugin` 或 `dir`）；回归 `laya-workflow-tests validate-capability-plugin`（11 断言：四正（id / `name` / `dir` / `entry`）+ 五负（无身份 / 仅无关键 / 空串）+ 两消息）。

- **`call the capability` 的表方言进了机器可读语法（P157，易用性）**：`bdd vocabulary` / MCP `bdd_vocabulary` 的 `dialects` 此前只广告**一种**表方言（动态候选 criteria），而 `call the capability "<cap>"` 步的 `| with.<k> | v |` / `| project.<state key> | <call 结果里的点路径> |` / `| chain.<as>.capability | <cap> |` / `| chain.<as>.with.<k> | v |` / `| chain.<as>.project.<k> | ptr |` 表 —— 参数化调用 + 状态投影 + 链式子调用，agentic workflow 的核心形状 —— 只活在散文里（`bdd/README.md`、`bdd/AGENT.md`、`docs/bdd_quickstart.md`），不在语法里，和 P107（动态 criteria 方言）同一类缺口：写的人能写、机器却不认。修法：`vocabulary_dialects()` 在其后追加第二条方言（步名 + 表头 + 每行前缀语义 + 编译形状 `{kind: call, capability, with, project, chain:[…]}`），并且回归**真编译**广告出来的方言 —— 一个没人能用的方言就是谎话。回归 `laya-workflow-tests bdd-vocabulary`（19 断言：原 17 + 方言存在 + 真编译 project/chain + 真 validate + 人读形式点名）。
- **一个 Scenario 只能带一个 action（P158，正确性）**：每个承载 action 的 `Then` 步编译成不同的 action 类型，而节点的装配是一条**优先级链**（`if !rules.is_empty() {…} else if …`）—— 于是第二个 action 被**静默丢弃**：`bdd build` 对一个同时有 `Then label …` 与 `Then call the capability …` 的 feature **退出码 0**，产出的 spec 里那个 `call` 干脆不存在（已实测复现）。修法：`compile_decision_node` 在装配之前收齐本 Scenario 的 action 步，**不止一种**类型即拒并点名两者；**重复的单值 action**（第二个 `gate` / `call` / `combine` / … 会覆盖第一个）同样拒；`threshold`（若干 `label …` 合成一条规则）与 `copy_keys`（累加）仍合法。语料安全：全量 feature 的 347 个带 action 的 Scenario **零混用**。回归 `laya-workflow-tests bdd-single-action`（3 断言：混用拒 + 重复 `call` 拒 + 多条同类规则仍编译）。

- **每个 option 声明的 JSON 类型必须和引擎读它的方式一致（P159，正确性）**：P150–P154 依次关掉了「数值域 / 闭集字符串 / 布尔 / 逗号列表 / 定长字符 / 字符串数组 / 对象容器」这几面，剩下最朴素的两面从未被看过 —— **普通字符串** option 与**有符号整数** option 拿到别的 JSON 类型时，`as_str()` / `as_i64()` 返回 `None`，解析器**静默回落到默认值**，而 `validate` 依旧绿：`"format": 5` 的 `datetime` 悄悄变成空格式、`"offset_secs": "60"` 悄悄变成 0、`"separator": ["\n"]` 悄悄变成空串。修法：新增 `STRING_OPTIONS`（覆盖 `as_str` 读的全部普通字符串选项，跨六十余个 kind）与 `I64_OPTIONS`（`as_i64`）两张表，`check_option_domains` 逐项校验；已被闭集校验（P151）或特例（`metrics.what`、`csv.delimiter`）覆盖的选项不再重复登记。语料零违规（仓库 dsl spec 与 BDD capability 行全扫）。
- **手维护的选项类型表必须证明自己还在描述解析器（P159，可审计）**：P150–P154 的类型表都是手写的，谁也不能保证它和 `parse_kind` 不漂移（P131 的教训）。新增 `capability::option_type_sites()`（`parse` 仍是私有，只开这一扇窗），回归拿**表里的每一条**构造一个错误类型的定义去过 `validate`，断言 ① 被拒 ② 被拒的理由**点名了这个 option** ③ 不是 `never reads`（后者意味着表里那条 `(kind, option)` 这个 kind 已经不读了）。一百二十余条全部通过；这条守卫在写成的当天就抓到一个**真 bug**（见下条）。
- **`plugin`/`name` 两个别名同时出现不再被误判（P159，正确性）**：`plugin` 解析器原本写 `get("plugin").or_else(|| get("name"))` —— `get("name")` 只在 `plugin` **缺席**时才被调用，于是 P128 的「声明了没人读的选项」检查永远看不到它：一个同时写了 `plugin` 与 `name` 的 capability（文档里这两个是同一件事的两个名字，写两个只是啰嗦，不是错）会被**拒**，错误还把 `name` 说成像拼错了一样。修法：两个 key **都无条件读**，`plugin` 存在时仍由它决定（语义不变）。回归 `validate-capability-plugin` 加三条（两个都写 / `script` 同理 / `plugin` 优先）。

- **选项的 JSON 类型改在“读的地方”声明（P160，正确性/可审计）**：P150–P159 的类型校验都是**旁路表**（`U64_OPTIONS` / `STRING_OPTIONS` / `BOOL_OPTIONS` / …），表可以漏、也可以和 `parse_kind` 漂移 —— P159 的守卫只证明了「表里每条都还活着」，**证不了表是全的**（它自己那张表就是一次有 bug 的扫描的产物，漏掉了 `plugin.plugin` 与 `or_else` 的懒读）。修法：把“读成什么类型”搬到读口 —— `Fields` 的通用读从 `get` 换成 `typed`，`s` / `u64` / `i64` / `f64` / `b` / `obj` / `arr` 各自在返回值之前断言 JSON 类型（不符则记进 `fields.wrong`，由 `report_wrong_types` 按 P150–P159 原来的先后顺序拒掉，**文案逐字不变**），只留两个逃生口：`any`（`body` / `expected` / `variables` 这类不透明值）与 `has`（存在性探测，类型由它真正的读口断言）。所有类型表连同 `option_type_sites()` 一并删除。**顺带抓到两个表漏掉的洞**：`plugin.op` 与 `web_fetch.method` 此前**完全没人验类型**（`"method": 5` 静默变成 `GET`），现在一并拒。守卫随之升级为**扫真源码**：① `parse_kind` 里不再有任何 `f.get(`；② 每个 `.any(k)` 的类型必须另有归属（不透明值 / `port` / `metrics.what` / `csv.delimiter` / `CLOSED_SETS`）；③ 每个 `has(k)` 在同一 arm 里必须有一个带类型的读；④ 把扫出来的**每一个**带类型的读口各喂一个该类型之外的值，断言被拒、且错误点名叫这个 option。语料零回归（仓库 dsl spec 与 BDD capability 行全扫）。

- **同一张表里重复的行键会静默顶掉前一行（P161，正确性）**：决策词汇表里所有 `| key | value |` 表都编译成**一个 JSON 对象** —— choice 问题的 `criteria`、`call` 步的 `with`/`project`/`chain`、`Given the policy`、`Given the capabilities`、`match_rules` 启发式的 label 映射 —— 于是同一张表里重复的 key **覆盖**前一行：作者写的第一条声明被丢掉，`bdd build` 仍然 0 退出。这是 P128「声明了没人读的选项」升一层、落在**编写层**：编译器现在逐表拒重复键，并同时点名两行（`line N: ... declares "X" twice (the first is at line M) ...`）。比较的是**编译器读到的原始行键**，所以语料里真实存在的 `with.text` 与 `project.text`（两张不同的 map）照旧合法，`with.text` 与 `chain.<as>.with.text` 同理。`score` 的 level 表是刻意例外：它的行编成**列表**，重复项被保留而非丢弃。语料零回归（全仓 feature 与 json 扫描 + 全量 features-check 全绿）；回归 section `bdd-table-key-once`（9 断言：六负 + 三正，每条负例断言「点名违规行 + 首现行行号」）。**诚实边界**：`score` 的 level 数组、以及 `render` / 序列化的输出回路不在此列（它们不产生对象键的静默覆盖）。

- **一步声明被同一 Scenario 里后面的步静默顶掉（P162，正确性）**：P161 关掉的是**表内**重复行键；再上一层，被丢掉的声明是一**整步** —— `edge_condition` 是按 answer 建的 map，`edge_default` / `min_confidence` / `max_retries` / 子工作流引用 / `the primary question` / `the action question` 都是 `Option`，`state.rename` 是按输出键建的 map，一个问题只装一个 `heuristic` 对象；后写的那步**覆盖**先写的，`bdd build` 仍然 0 退出 —— 而丢掉的是一整条**路由**或**节点级设置**，节点行为会**悄悄改变**（不只是少一行表格数据）。修法：新助手 `step_once(declared, what, line)`（表层 `table_key_once` 的姊妹）+ `set_heuristic(…, lq, …)`（键 = 问题 id），接 15 处；错误同时点名两行（`line N: this node declares <what> twice (the first is at line M) …`）。键按节点 / 问题计，所以语料里**正常**的形状照旧合法：一个 Scenario 里每个问题各一条启发式（agents/* 全是这形状）、一条具体路由 + 一条 catch-all、不同 answer 各自路由都放行；`keep the state key` 是**列表**（重复被保留）——刻意列为例外。语料零回归（features-check 204/204）；回归 section `bdd-step-once`（10 断言：7 负 + 3 正）。

- **手写 / 侧载的 JSON spec 现在也守 `project` 契约 = 两条路径同一份判定（P178，正确性 + 可维护性）**：P165 的三条 `project` 护栏（指针不是 JSON 字符串 ⇒ 引擎 `as_str()` 跳过、`state.<key>` 永不写入而 `@outputs` 仍绿；投影键为空 ⇒ 没有任何 `${state.<key>}` 能寻址；`chain` 行显式给了空别名 ⇒ 结果落在谁都摸不到的名字下）此前和 P164/P166/P175 一样**只活在 BDD 编译路径**。`laya-workflow validate --spec hand.json` 在手写 JSON 上原样放行 —— 实测（真实跑，改前，安装版二进制）：一份 `project.count = 3` / `project."": …` / `chain[].as = ""` / `chain.x.project.ok = true` 的手写 spec，四种形状逐一 `validate --spec` **全部 EXIT=0**；同样的东西进 `.feature` 会被 `bdd build` 拒。修法：判定收敛到 `capability::call_project::{project_step_issue, project_issue_body}`（判词与消息从 `bdd.rs` 迁出，`guard_call_project` 变成只加 `line {n}: ` 前缀的薄壳），`spec.rs` 的守卫（P177 的 `guard_call_with_spec` 更名 `guard_call_spec`）在 `with` 之后接**同一个**函数、用 `node {name}: ` 前缀。一处**语义差异**被显式处理：spec 里 `chain` 条目的 `as` 是**可选**的（缺省回退到 capability 名），所以只有**显式写成空字符串**的 `as` 才算「空别名」；BDD 编译路径永远写字符串 `as`，行为与 P165 完全一致。真跑（改后）：上述四份手写 spec `validate --spec` 全部 **EXIT=1**（`node a: ` 前缀，分别点名 `project.count` / 空名 / 空别名 / `chain.x.project.ok`，并说明 `state.count` 永不写入），而「`project` 全为字符串、含无 `as` 的 chain 条目」的 clean spec 仍 EXIT=0；dsl 全树 163 个 spec 走严格校验 **0 误拒**。回归段 `laya-workflow-tests validate-call-project`（24 断言：4 正例 / 指针类型 ×4 / 空键 / 空别名 / chain 指针 + `project_step_issue`/`project_issue_body` 的共享判定 + 「无 `as` 合法」），并与 P165 的 `bdd-call-project` 同跑。
- **节点 / spec 的值写错类型 = 声明的值被默认值静默替换（P179，正确性 / 易用性）**：P148 收的是 spec / policy 的**键**名、P168 收 policy 值的**类型**，这一条收 **node / spec 自身的值**类型。解析器对每个结构值都用带类型的读取口（`as_f64` / `as_u64` / `as_str` / `as_object`），拿不到就**静默回落到默认**：`"min_confidence": "0.9"` 读成 `0.0`（本要卡的门槛消失，所有路由放行）、`"max_retries": "5"`（或 `-1` / `2.5`）读成引擎默认 `2`、`"edge.default": 5` 读成 `None`（节点**根本没有**兜底路由）、`edge: 5` / `questions: "q"` / `action: "copy"` 整体被丢、`"convergence_window": "3"` 与 `"convergence_eps": "0.001"` 被忽略。实测（真实跑，改前，安装版二进制）16 份手写 spec 逐一 `validate --spec` **全部 EXIT=0**；同样的值进 `.feature` 编译器永远写正确类型，所以只有手写 / 侧载 JSON 会踩。修法：`spec.rs::guard_spec_value_types` 接在 `guard_call_spec` 之后收这些值 —— 只判**类型**（`min_confidence ∈ [0,1]` 是另一条轴，由 `validate_graph_semantics` 守），且 **JSON `null`（describe / round-trip 表达「可选值缺席」的写法）与含 `${...}` 的字符串模板（引擎运行期展开）一律不判**，所以 `bdd round-trip` / `import-check` 的 163 份 spec 与 describe 产物 0 误拒。真跑（改后）：上述 16 份全部 **EXIT=1**（消息点名键、实际 JSON 类型、读取口与后果，如 ``node a: `max_retries` is a string — the engine reads it with `as_u64()` and silently keeps the default 2``），clean / `action: null` / `edge.default: null` / `${X}` 模板正例仍 EXIT=0。回归段 `laya-workflow-tests validate-spec-value-types`（24 断言 = 7 正例 + 17 反例：spec `name` / `convergence_window` ×2 / `convergence_eps` / `min_confidence` ×2 / `max_retries` ×3 / `edge.default` / `edge` ×2 / `edge.condition` / `questions` ×2 / `action` / `primary_q`，并钉 `as_f64()` / `as_u64()` / `as_str()` 三个读取口字面）。

- **`convergence_window: 0` / 负的 `convergence_eps` = 收敛判据被静默做成「立刻收敛 / 永不收敛」（P180，正确性 / 易用性）**：P179 收的是 node / spec 值的**类型**，这一条收**范围**（P168 类型 / P173 范围 的镜像，落在 spec 的两个收敛旋钮上）。运行期 `workflow.rs` 的收敛判据是在 `score_history[len - convergence_window..]` 上取 `mn`/`mx` 再比 `mx - mn <= convergence_eps`：① `convergence_window: 0` ⇒ 窗口切片为**空**，`fold` 得 `mn = +inf, mx = -inf` ⇒ `mx - mn = -inf <= eps` **恒真** ⇒ 节点**只跑第一个**就 `break`，`final_action: "converged"`、`loop_detected: true`，工作流静默地「声称收敛」；② `convergence_eps: -0.5` ⇒ `mx - mn >= 0` 永远满足不了 `<= -0.5` ⇒ 判据**永不触发**，只能一路跑到 `max_iterations`。实测（真实跑，改前，安装版二进制）：两节点 `a→b`（`max_iterations: 8`）状态 `{"score":0.5}`，窗口 3 时 `run` 走完 `a,b` 得 `final_action: "stop"`（step_count 2），窗口改成 **0** 则同一份 spec `final_action: "converged"`、**step_count 1**（`b` 根本没跑）、`EXIT=0`；自环节点 + `max_retries: 9` + 窗口 2 时，`eps = 0.01` 第 2 步 `converged`，`eps = -0.5` 判据从不触发、一路 8 步到 `max_iterations`。修法：新函数 `spec.rs::guard_spec_value_ranges(spec)` 接在 `guard_spec_value_types` 之后，只判**范围** —— `convergence_window >= 1`、`convergence_eps >= 0`（`max_iterations >= 1` 另有守卫、`min_confidence ∈ [0,1]` 在 `validate_graph_semantics`）。真跑（改后）：`window: 0` 与 `eps: -0.5` 的 spec `validate --spec` **EXIT=1**（点名「空窗口 ⇒ `mx - mn` 为 -inf」/「负容差永远满足不了」），合法值（`window` 1/3/5、`eps` 0 / 1e-4）仍 EXIT=0。回归段 `laya-workflow-tests validate-spec-value-ranges`（7 断言：5 正例 + `window: 0` + 负 `eps`）；语料扫描确认 163 份 spec 只用 `convergence_window` ∈ {3, 5}、`convergence_eps` > 0，**0 误拒**。

- **问题 `type` 写歪（或没写）= 问题被静默当成 `choice`（P181，正确性 / 易用性）**：引擎读一个问题的 `type` 用的是 `unwrap_or("choice")`（`backend.rs` / `workflow.rs` / `bdd.rs` / `bdd_mcp.rs`）与 `unwrap_or("boolean")`（`rules.rs`），所以写歪的 / 缺失的类型被**静默替换**成 `choice`：这个问题于是按 choice 被回答与路由（它的答案去 key 节点的 `edge.condition`），工具链也照样报成 `choice`，作者永远看不到这处手滑。实测（真实跑，改前，安装版二进制）：一份「score 形状（`criteria` 是数组）」的问题，`"type": "score"` 时 `run` 得数字答案 `1.0`、无边可匹配、停在节点 `a`；把类型手滑成 `"scor"`（或 `"chocie"`）后**同一份 spec、同一个 state、`validate --spec` 同样 EXIT=0**，但 `run` 的答案是字符串 `"A"`、命中 `edge.condition.A` 于是**路由到 `b` 才停** —— 一次类型手滑静默改了整条决策路径。修法：`validate_graph_semantics` 的问题循环里新增类型白名单 `{choice, score, noul, boolean}`（`boolean` 是 rules 后端读的），**未知值直接拒**（带 `did you mean "choice"?` 建议），**缺 `type` 也拒**（引擎把缺省读成 `choice`，同一个静默默认）。真跑（改后）：`"scor"` / `"chocie"` / 未知类型 / 缺 `type` 的 spec `validate --spec` **EXIT=1**，消息点名问题、实际写的值、引擎认的集合与后果；`choice` / `score` / `noul` / `boolean` 四类与语料全树仍 EXIT=0（163 份 spec 的 746 个问题只用 choice 642 / score 35 / noul 69，**0 误拒**）。回归段 `laya-workflow-tests validate-question-type`（10 断言：4 类型正例 + 带 heuristic 正例 + `chocie` 拒 + did-you-mean + `scor` 拒 + 缺 `type` 拒 + 非字符串 `type` 拒）。

**当前语料现状**（本段每个数都由 `bdd doc-check` 从门禁复算，改了不更新就会点名）：`bench/dsl_smoke_expect.json` 覆盖 **127** 个 spec / **988** 个 state（多节点 spec 的每个样本按 P38 逐步钉 `trace.step_count` + 每步 node/action/answer）；`bench/dsl_smoke_states.json` 注册 **128** 个 spec / **989** 个 state；**分支覆盖门禁** 断言每个 state-registered spec 的可达节点全集被走到（白名单仅 1 条，容器节点已结构性排除）；覆盖台账 `128 offline-verified + 35 live-declared = 163 specs`。门禁实测：`scripts/bdd/check.sh` 全绿、`dsl smoke 163/163`、`bdd round-trip 163/163`（回归断言的条数、全量 `laya-workflow-tests` 的 section / passed 数只出现在 CI 输出里，不再写进文档 —— 一个没人复算的数一周就会变成谎话）。

### 作者循环（agent 怎么写一个决策 workflow）

1. 想清楚决策图：几个节点？每个节点问什么问题、答什么路由、产出什么 label/动作。
2. 绿场起点：**MCP `bdd_new`**（`name`+`cat`+`intent` → 最小合法 `@decision` `.feature` 骨架，
   自验证能过 `bdd build`；`write=true` 落盘、`root` 指定工作区）或 CLI `laya-workflow bdd scaffold`。
3. 在 `bdd/workflows/<cat>/<name>.feature` 扩展。**先把词汇表拉下来**：CLI `laya-workflow bdd vocabulary`（`--json` 给工具吃）或 MCP **`bdd_vocabulary`** —— 返回决策图全部步骤模板（按 given/when/then 分组，即 did-you-mean 索引那份）—— 照模板替换 `<占位符>`，生造措辞会被拒。
4. 校验：MCP `bdd_validate`（喂 feature 文本/路径 → per-scenario compile + step coverage +
   validate 逐行错误）或 CLI `laya-workflow bdd build`。拼错会收到 **`line N:` + `did you mean ...?`**
   （P28 步骤层 + P34 语义层 + P35 行号），照建议在对应行改即可。
5. 出 spec：**MCP `bdd_transpile`**（feature → dsl spec，`@decision` 单图 / browser 逐 scenario；
   dsl_version 剥离对齐 dsl 约定；`write=true` 落盘 dsl/<cat>/ 带 exists 防覆盖）或 CLI
   `laya-workflow bdd transpile <file> --out dsl/<cat>`。
6. 造册审计：MCP `bdd_catalog` —— 双向完整性（dsl↔feature），报 orphan_specs / features_without_spec。
7. 反向搬运：**MCP `bdd_import`**（已有 JSON workflow spec → `@decision` feature，附 `graph_matches` 往返证明；批量走 CLI
   `laya-workflow bdd import --dir <DIR> --into <cat>`）—— 让「把已知 workflow 转成 BDD」也能在 MCP 里一把完成。
8. 运行决策：先 **MCP `bdd_list`** 发现可用 workflow（返回每个 `@decision` 图的 `cat`/`name`/`description`/`start`/`nodes`/
   每问 `questions`（id+type+`answer_field`）/ `inputs`（离线调用要喂的 state 字段＝每问 heuristic 的源字段 `answer_field`/`field`/`extract_numeric` ＋ 动作里
   所有 `${state.X}` 插值 ＋ 类型隐含读（如 `ui_proposal` 的 `surface`/`snapshot_hash`））/ `outputs`（各节点能**发出**的 label：阶梯 label / gate 的 BLOCK·ALLOW·CONFIRM / combine 的 `route`（choice criteria 去掉 fallback，再加
   review_label）/ rubric 的 `status`（scored·human_review）；单节点图即全量、多节点图是并集，真正返回的是走到停下那节点的 label）/ `routes` + `default`
   （每节点 `edge.condition` 的 answer→目标映射与兜底目标 —— 多节点图据此读成 DFA，也据此判断某 label 会不会被继续路由而不返回）/ `offline`（true＝该图经 `dsl smoke`
   离线行为验证，离线 `bdd_decide` 可信；false＝只在 live 验证过——`verified_by` 指 gate、`why_live` 说明原因，离线调用只是默认走查）+ 顶层 `offline_count`/`live_count`）
   —— `bdd_list` 递归扫 `dsl/` 子树（与 `bdd_decide {name}` 的解析同源，`cat` 取相对子路径，如 `routing/sub`）；再用 **MCP `bdd_decide`**
   （`name` 或 `feature_text`/`feature_path`/`spec_path` + `state` → `label`（终态节点的决策投影：threshold label / gate_action / combine `route` / rubric `status`，都没有才回落 `stop`）+ 全 `trace` + `result` + 决策契约
   `inputs`/`missing_inputs`/`offline`/`verified_by`/`why_live`，与 `dsl smoke` 同一离线确定性引擎）跑它：`missing_inputs` 非空说明有声明字段没喂、
   label 可能来自默认值；`inputs` 为空说明离线引擎确实不读 state（该图需真实模型后端驱动）——
   让 BDD 图成为 agent **可发现、可调用、且诚实**的决策核心，而不只是可写的产物。
9. 全量门禁：`laya-workflow bdd round-trip`（160/160 复现）+ `scripts/bdd/check.sh`。
10. 提交时 `bdd round-trip` 会拦：dsl 有 spec 但没 `@decision` 源 = FAIL。

### 为什么这样是 agentic workflow 的核心

- **确定性**：`@decision` 词汇表是确定性编译器（正则 → 决策图），0ms、无歧义；validate 双保险。
- **正确性可证**：语义图校验 + 决策输出断言 + **决策 trace 全钉** + offline-detection，让"决策对没对"是
  可测、可复现、可回归的（P24-P31），不只是"能编译"。
- **单一事实来源**：`.feature` 是源，`dsl/*.json` 是编译产物；round-trip 证明等价，杜绝双份漂移。
- **可直接运行 / 可被 agent 调用**：`laya-workflow run --spec dsl/<cat>/<name>.json` 用 HeuristicBackend / 真实 LLM 跑决策图；MCP `bdd_decide` 让同一张图在进程内被 agent 直接调用（feature/spec + state → label + trace）。
